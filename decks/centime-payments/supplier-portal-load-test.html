Scale & Load — Suppliers, Bills, Invites & Payments

Local PG 17 stack (= Aurora 17.7 planner, co-located) · synthetic load · pre-schema-rationalization baseline · drivers in scripts/local/

Executive summary

  • Read path scales predictably to 5,000 suppliers / 10,000 bills — list-page p95 stays single-digit ms. The cost that grows is shared-buffer reads, ~linearly with population, because rows are wide (~2.3 KB — the enriched/track_search blobs). That is precisely the dial schema rationalization turns.
  • Found & fixed a hard scaling bug. Submit-for-payment 500-errored past ~300–500 bills (a single .in('id', billIds) blew the PostgREST URL limit). Chunked the loads → now handles 5,000 bills in one request (803 payments, 452 bills/sec).
  • Two client-side-aggregation hotspots dominate at volume: the supplier list pulls every heavy-vendor bill into JS (646 KB at 10k) and the analytics carousels fetch the whole dataset (and overflow the browser cache). Both want a server-side aggregate.
  • Bulk invite is email-safe (every invite landed in local Mailpit, none to Resend) but is a sequential per-supplier Clerk-user create — the real bottleneck, and the dev Clerk instance hard-caps at 100 users.
  • Method: we measured more than wall-clock — query plans, shared buffers, payload bytes — because raw p95 is noisy while those structural metrics are the stable truth.
Scope & method. Synthetic Track-A load: real company names (SEC EDGAR), fabricated everything else (bc+…@centime.com contacts, format-valid EINs, Apollo/MC-shaped blobs). Deterministic seed (identical data every run → clean before/after a schema change). Read-path measured via direct EXPLAIN(ANALYZE,BUFFERS) probes of the real hot queries; write-path via the real authenticated endpoints. No live Apollo/Mastercard, no real email, no money moved.

Read path · Supplier list (the hot CP surface, 200 → 5,000)

The bills hotspot: the supplier list's "active-vendor" bill aggregate pulls every heavy-supplier bill into the handler to sum in JS — 4,063 rows / 646 KB at 10k bills, planner falls back to a sequential scan. A DB-side GROUP BY would return ~50 rows. Loading one heavy supplier's 100 bills is cheap (142 KB) — batch-pay isn't the bottleneck; cross-supplier aggregation is.

The bug: the handler loaded the whole selection via one .from('bills').select(…).in('id', billIds); a few hundred UUIDs overflow the PostgREST request URL → HTTP 500 "Failed to load bills". A user selecting 500+ bills to pay hit a hard failure.
The fix: new api/lib/pg-chunk.js (selectInChunks / updateInChunks, chunk 200) applied to the bill load + the per-group link update. Re-validated end-to-end: 5,000 bills → 803 payments in one request, all pending_approval, 0 executed (money-safety enforced via a temporary $0-floor approval policy, restored after).
